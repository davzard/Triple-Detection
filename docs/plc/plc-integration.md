# PLC 对接说明（电气 / PLC 工程师）

> 适用：Triple-Detection 三期 OCR 检测系统 ↔ PLC（Modbus TCP）
> 版本：v1.1（新增心跳通信看门狗）
> 基地址：保持寄存器 40001 起，偏移 0 计数；Modbus TCP，UnitId 默认 1，端口 502

本系统通过 Modbus TCP 与 PLC 交互。本文档给出**寄存器表**、**交互时序**，以及最关键的**心跳通信看门狗**约定——它保证"检测软件崩溃/卡死时，PLC 能自行把产线停到安全状态"，不依赖 PC 侧任何存活代码。

---

## 1. 寄存器表

| 偏移 | 寄存器 | 方向 | 含义 |
|---|---|---|---|
| 0 | 40001 TRIGGER | PLC → App | 触发信号。上升沿（0→非0）表示一个产品到达检测位。App 读沿并做抖动过滤 |
| 1 | 40002 RECIPE_CHANGE | PLC → App | 换型信号。上升沿表示配方切换，App 读取 40003 |
| 2 | 40003 RECIPE_ID | PLC → App | 目标配方/产品 Id（App 侧任务映射） |
| 3 | 40004 LINE_SPEED | PLC → App | 线速（预留，App 当前仅读取） |
| 10 | 40011 RESULT | App → PLC | 检测结果：0 空闲 / 1 OK / 2 NG |
| 11 | 40012 RESULT_VALID | App → PLC | 结果有效脉冲（与 RESULT 配合，PLC 读沿判定） |
| 12 | 40013 REJECT_CMD | App → PLC | 剔废命令脉冲：1 → 100ms → 0，PLC 侧驱动剔除机构 |
| 13 | 40014 LINE_STOP | App → PLC | 产线停机命令（置 1 请求停机，PLC 侧处理） |
| 14 | 40015 ALARM_CODE | App → PLC | 安灯报警码（电气侧显示；0 = 清除）。见 §4 报警码表 |
| 15 | 40016 STATION_STATUS | App → PLC | 工位状态：0 空闲 / 1 运行 / 2 报警 |
| **16** | **40017 HEARTBEAT** | **App → PLC** | **App 存活心跳：自动运行期间 App 每秒写入递增计数（0→1→2→…→65535→0 循环）。PLC 侧监视，见 §3** |

> 偏移 4–9 预留。剔除参数（延迟/持续 ms）默认由 PLC 侧固定配置；如需 App 下发，可在预留区扩展。

## 2. 正常交互时序（自动运行）

```
PLC                    App
 │  产品到位，40001 触发 ↑  │
 │ ────────────────────────▶ │  App 读到触发沿
 │                           │  运行 OCR 检测
 │                           │  写 40011 RESULT = 1(OK)/2(NG)
 │  读 40011/40012 判定  ◀──── │  写 40012 RESULT_VALID 脉冲
 │  NG → 40013 剔废脉冲       │  （NG 时 App 主动写 40013）
 │  继续走带                   │
```

- 检测节拍由 PLC 触发驱动，App 被动响应，**App 不控制走带**。
- 连续 NG 达到阈值（默认 10，可配）→ App 写 40014 LINE_STOP + 40015 ALARM_CODE=1001。

## 3. 心跳通信看门狗（安全关键）

### 为什么需要

传送带由 PLC 驱动，App 只是 Modbus 客户端。**如果 App 崩溃 / 卡死 / 断电 / 断网，PLC 默认不会知道**——产线会继续走带，但没人检测、没人剔废，NG 品会被当 OK 品放行。这是食品/药品产线最危险的场景。

### 约定

1. **App 侧**：产线处于**自动运行**状态时，App 每 **1 秒**（可配 `HeartbeatIntervalMs`，默认 1000）向 **40017 HEARTBEAT** 写入一个**递增计数**（16 位，到 65535 后回绕 0）。非自动运行状态（空闲/就绪/暂停/报警/下班）**不写**——此时产线不在 App 的自动检测控制下，PLC 不应要求心跳。
2. **PLC 侧**：设一个**看门狗定时器**，监视 40017 的值是否变化：
   - **仅当产线处于自动运行模式**时启用监视（与 App 写心跳的条件一致）。
   - 若 **≥ 5 秒**（建议 5000ms，即 ≥5 个心跳周期，容忍偶发通信抖动）内 40017 **没有任何变化** → 判定 App 失联 → **立即停止传送带**（安全状态），并置一个"通信丢失"报警（可复用 40015 或独立 IO/安灯）。
   - 40017 恢复变化（App 重启并重新进入自动运行）→ 通信恢复，报警复位，操作员可重新启线。

### 参数建议

| 参数 | 建议值 | 说明 |
|---|---|---|
| App 心跳周期 | 1000 ms | App 侧 `HeartbeatIntervalMs` |
| PLC 看门狗超时 | 5000 ms | ≥ 5 倍心跳周期，容忍网络抖动/偶发丢帧 |
| 超时动作 | 停传送带 + 通信丢失报警 | 安全状态优先 |
| 监视启用条件 | 产线自动运行模式 | 与 App 写心跳条件严格一致 |

### 为什么阈值是 5 秒而不是更短

- 太短（如 1–2s）：Modbus TCP 偶发丢帧、PLC 扫描周期抖动就可能误触发停线，产线频繁误停。
- 5s 在"安全响应速度"和"抗抖动"之间是工业常用折中。若产线节拍极快、对放行风险极敏感，可下调到 3s，但需同步把 App 心跳周期降到 500ms。

## 4. 报警码表（40015 ALARM_CODE）

| 码 | 含义 | 触发 |
|---|---|---|
| 0 | 无报警（清除） | 操作员复位 / 下班 / 退出 |
| 1001 | 连续 NG 达阈值 | 连续 NG 次数 ≥ 阈值（默认 10） |
| 2001 | 相机心跳丢失 | 运行中相机无新帧 > 阈值（默认 30s） |
| 2002 | 检测方案崩溃 | VM SDK 方案崩溃且自动重载超限 |
| 3001 | PLC 断线（StopLine 策略） | App 检测到与 PLC 通信中断 |
| 4001 | 连续检测超时 | 连续超时 3 次 |
| 5001 | 换型配方不存在 | 换型信号对应的产品/任务未配置 |

> PLC 侧"通信丢失"报警（§3 看门狗触发）建议用**独立**的报警位/安灯，不要占用上表 40015 的码值——因为该报警是 **PLC 自己产生的**（App 已失联，无法写 40015）。

## 5. 安全机制分层（给评审用）

| 层 | 机制 | 防什么 | 依赖谁存活 |
|---|---|---|---|
| PLC 侧 | 心跳看门狗（§3） | **App 崩溃/卡死/断电/断网** → 产线继续走带无人检测 | **仅依赖 PLC**（App 死了也生效）✅ 保命层 |
| App 侧 | 相机心跳丢失报警 2001 | 相机掉线但 App 还活着 | App 存活 |
| App 侧 | 连续 NG/超时 → LINE_STOP | 检测质量异常 | App 存活 |
| App 侧 | PLC 断线 → StopLine 策略 | App 连不上 PLC | App 存活 |
| 系统侧 | Windows 看门狗服务（后续） | App 崩溃后 30s 内自动重启，尽快恢复检测 | 独立服务 |

**核心原则：安全机制不能依赖"被监控对象"（App）存活。** 所以"App 死了要停线"这件事必须由 PLC 侧的心跳看门狗保证，App 侧的 Windows 看门狗只负责"尽快把检测能力拉回来"（恢复，不是保命）。
